### F. 1초의 정체 — 서버 SCTP datagram 이어붙이기

봇 SCTP trace + 서버 `sctp-proto` trace 교차(서버는 부장님이 `RUST_LOG` 켜고 재기동):

```
sending ppi=53 tsn=…332 ssn=1 len=8      ← floor GRANTED
sending SACK: cumTsnAck=…
sending 64 bytes (total 2 datagrams)     ← 둘을 이어붙여 1 회 send → GRANTED 유실
…333 → total 1 → 정상 도달
…334 → total 1 → 정상 도달
T3-rtx timed out → retransmitting tsn=…332   (1005ms 뒤)
```

`Payload::RawEncode(Vec<Bytes>)` 의 각 원소는 **독립된 SCTP 패킷**(공통헤더 12B)인데
`encode_payload` 가 전부 이어붙였다. 수신측은 SCTP 패킷 하나로 파싱하므로 두 번째
이후가 통째로 버려진다 → 유실과 동일 → RTO.Min(1s) 후 재전송.

**`total 1` 은 100% 도달, `total 2` 만 유실**이라 결정론적이었고, 그래서 망 문제로
보이지 않은 채 오래 살아남았다.

### G. 수리 (커밋 62d1097)

- `send_transmit` 이 chunk 마다 개별 DTLS 레코드로 전송. `encode_payload` 삭제.
- **`oxrtc/src/dc/mod.rs` 에 같은 코드**가 있었다(주석 "서버 drain_transmits 거울",
  함수 설명 "DTLS application data 1건"인데 N건을 1건으로 뭉갬). 복사되며 결함까지
  전파된 경우라 같이 수리.
- 호출처 전수: oxsfud 2곳·oxrtc 2곳이 각각 같은 함수를 쓰므로 함수 한 곳씩으로 전부 덮임.

| 지표 | 수정 전 | 수정 후 | 기준 |
|---|---|---|---|
| KPI 1 access | 1005~1048ms | **2~5ms** | 300ms |
| KPI 2 e2e | 1382~1402ms | **359~389ms** | 1000ms |
| 화자전환 공백 | 1008~1024ms | **2~4ms** | 600ms |
| `gating_correct` idle 누수 | 38 패킷 | **0** | — |

gating 누수는 별개 결함으로 보였으나 **grant 지연이 열어둔 창**이었다 — 같은 뿌리.

부장님 증언: **"1pc 시험하면 5번 중 2~3회 실패해서 재시험했는데 깔끔하다."**
1pc 는 단일 PC 에 pub/sub 이 모여 DATA+SACK 이 한 배치로 묶일 확률이 높다 —
`total 2` 가 자주 생겨 실패율이 높았던 것으로 설명된다.

### H. KPI 2 내역 (튜닝 좌표)

수정 전 SCTP trace 구간 분해:

| 구간 | 소요 |
|---|---|
| WS 연결 + IDENTIFY | ~10ms |
| ROOM_CREATE / ROOM_JOIN 응답 | 3.7 / 2.7ms |
| **ICE + DTLS 수립** | **~283ms** ← 전체의 대부분 |
| SCTP INIT → DC open | ~5ms |
| 봇 `open_sctp_datachannel` 폴링(`sleep(0.1)`) | ~100ms ← **시험 도구 아티팩트** |
| floor REQUEST → GRANTED | 2ms |

**시그널링은 총 17ms 로 사실상 공짜다.** 무겁다고 예상하던 부분이 아니라
ICE/DTLS 에 몰려 있다. 봇 폴링 100ms 를 빼면 실질 KPI 2 ≈ **290ms**.

## 진행 · 20260814 22:xx — soak 중 별건 적발·수리 (`floor_seam` 오탐)

soak 8회 중 2회 빨강. 찾던 seq 결손이 아니라 **`conf_ptt_relay` 의 `floor_seam`** 이었다


503ms 가 `MBCP_T132_MS`(500) 와 같아 재전송으로 의심했으나 **시나리오 RELEASE→REQUEST
간격**이었다(`at:3` → `at:3.5`). 또 설계값을 신호로 오인할 뻔했다.

규명(봇 dump + 서버 로그 + 서버 소스 교차, 단독 12회 중 2회로 재현):

  botB GRANTED 4.1353 → 첫 송신 4.1473 확인. GRANT 없이 안 보낸다.

  RELEASE 마무리 silence flush 3프레임 + grant 예열 CN 을 같은 slot 으로 broadcast 한다
  (서버 로그 `[PTT:REWRITE] silence flush 3 frames`). 설계대로다.
- **등식 결함** — 옛/새 화자를 GRANTED **통지 도착 시각**으로 갈랐다. 예열 CN 은 통지와

  500ms 로 부풀었다. 17~25% 레이스.
